# 项目展示与简历条目（当前可核对版本）

## 30 秒介绍

我开发了一套 AI 用户反馈与技术工单处理平台，用自己的微信小程序作试点。它管理产品资料和反馈，模型在有限的只读工具中选择检索或任务人数核对，生成有文档依据的处理建议；开发者人工核对后才会建立工单。每一步的工具、模型和错误信息都留下记录，便于复盘失败案例。

## 当前已经完成并可现场展示

- React + TypeScript 工作台：项目切换、资料录入、反馈收件箱、分析依据、执行记录和工单列表。
- FastAPI + SQLite：项目、资料、反馈、分析、工单与 Trace 持久化；历史分析刷新后可恢复，不需重新消耗模型调用。
- Docker Compose：使用多阶段前端构建、API/Web 健康检查、仅本机端口映射和 SQLite 命名卷；实际验证容器重启后数据仍可恢复。
- 受控模型工作流：先选只读工具，再生成建议；BM25 对英文词、中文单字和二元词排序并记录安全诊断；引用必须对应当前项目检索到的资料原文；模型不可用时明确降级，并记录每阶段耗时与 token 用量。
- 审批安全：区分有依据的建议、资料不足和运行失败。资料不足时 API 拒绝建单，补资料后可重试。审批校验分析版本和引用，存储原始建议、人工标题及审核 Trace。重复审批返回同一工单。
- 工单闭环：支持待处理、处理中、已完成的单向状态机，完成时强制填写解决说明，重复请求幂等且状态变化可审计。
- 事实与验证：2026-11-18 离线流程 36/36 通过，6 条无答案题全部进入「待补资料」并拒绝建单。使用同一题集中 30 条可回答题做检索回归，BM25 Recall@1 为 30/30。本机通过 136 项后端测试、10 项前端请求测试、lint/build、隐私门禁和 HTTP 冒烟。

2026-10-21 使用 DeepSeek V4.1 Flash 追加真实接口复测：36/36 分析可用，逐题辅助复核 35 条符合参考、1 条待作者确认，6 条故意无答案题未编造所问数字、日期或设备结论。共 72 次请求，58,887 token，整条分析 P95 为 5.045 秒，费用未知。这是 Codex 辅助复核，不能称为作者签字的独立人工准确率。**没有真实试用者数量或业务提效数据**。完整证据见 [真实接口复测](真实接口复测-20261021.md)。

## 当前简历项目条目示例

**AI 用户反馈与技术工单处理平台｜独立开发｜2026.09–至今**

- 开发 React/TypeScript + FastAPI/SQLite 反馈工作台，实现 BM25 检索、只读工具调用和引用校验。用事务约束建单资格、审核版本和重复提交，资料不足时拦截建单，补资料后可重新分析。
- 建立 36 条固定题离线回归与逐题 HTML 报告，覆盖 6 条无答案建单拦截，30 条可回答题检索 Recall@1 为 30/30。曾完成 36 条真实模型复测并记录 Token 与 P95。

**面试演示**：先用 `known-07` 查看原文、确认建单，再用 `unknown-01` 展示「待补资料」和执行记录。技术追问可以打开 `server/main.py` 的审批事务和 `server/tests/test_api.py` 的恢复用例，讲清楚旧版分析、过期审核和直接请求为什么都无法绕过服务端判断。有引用只能说明这段文字确实出现在模型的上下文中，是否支持结论仍由审核人判断。

简历仓库链接：https://github.com/abalika/signal-ai-feedback-platform 。面试时可以说：“我把回放流程、检索命中、真实模型语义和运行成本分开评估；真实复测没有硬凑满分，保留了一道题集口径待确认的案例。”

投递岗位若偏后台开发，先讲接口、数据库、审批幂等和异常处理；若偏 AI 应用开发，先讲任务流程、工具、引用与评测。能否写成“真实用户使用”“准确率提升”须以后续实际试用和人工评测为准。
