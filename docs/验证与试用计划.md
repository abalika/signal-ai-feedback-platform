# 验证与试用计划

## 证据规则

产品功能资料来自作者现有的微信小程序代码与测试。`examples/miniapp/` 中的文字是对可核对事实的整理，不代表企业客户资料。任何演示反馈均明确标记「模拟」；真实反馈另行记录，并在得到试用者同意后脱敏。不得在简历把模拟数据、模型输出或未完成部署写成实际业务结果。

## 固定测试集

先从产品代码和测试整理至少 30 条问题，包含：能从资料回答的规则问题、需要算数/核对规则的问题、资料中没有答案的问题、不同产品串用资料的隔离问题、工具失败与重复审批问题。每条标注预期答案、所需依据、是否允许建立任务。按开发集与最终测试集分开，修改提示词时不偷看最终集的结果。

评测记录最少包含：回答是否正确、引用是否对应原文、无依据时是否拒答、工单标题是否可执行、是否错误写入工单、响应时间和 API 错误。用直接模型回答与平台工作流作对照。失败样本保留原始输入、执行记录、问题归因、修改及复测结果；不只挑成功案例展示。

## 试用

邀请愿意测试现有小程序的同学完成具体任务，记录他们提交反馈的原话，以及开发者手工处理和借助平台处理的实际时间。试用人数和处理条数尚未产生，报告时按实际数据填写。分析时间差只作该批任务的描述，不在小样本上宣称统计显著或商业收益。

## 面试展示

准备 3 分钟演示：真实场景与反馈 → 文档依据 → AI 处理路径 → 人工确认 → 记录结果 → 一个 Bad Case 如何修复。另备代码入口、架构图、API 与数据库设计、测试运行方法。面对追问能够解释哪里由 AI 编程辅助生成、哪里由本人检查和修改。
